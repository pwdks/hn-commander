# 토큰 효율 지침

토큰은 크게 세 곳에서 샌다: **(1) 매번 읽히는 지침**, **(2) 읽는 파일과 명령 출력**, **(3) 모델이 쓰는 답변**.
아래 규칙은 이 셋을 줄이는 순서로 정리했다.

## 1. 매번 읽히는 것을 줄인다
- 지침 파일(`CLAUDE.md`/`AGENTS.md`)은 100줄 이하. 설명은 `docs/`로 빼고 안내 한 줄만 남긴다.
- 큰 기준 문서는 "전체를 읽지 말고 필요한 절만" + 절 목차를 지침에 적어 둔다.
  - 예: `docs/spec.md — 1 개요 | 2 구조 | 3 API | 4 DB (필요한 절만 읽을 것)`
- 지침 파일에 코드 예시, 긴 표, 변경 이력을 넣지 않는다.

## 2. 읽는 양을 줄인다
- 탐색은 검색(grep/glob)으로 범위를 좁힌 뒤 필요한 파일만 연다. 레포 전체 훑기 금지.
- 큰 파일은 필요한 줄 범위만 읽는다.
- 방금 수정한 파일은 다시 읽지 않는다.
- 이미 대화에 나온 내용은 다시 찾지 않는다.
- 읽지 말 것 목록을 지침에 적는다: `node_modules`, `dist`, `build`, `.next`, `coverage`, 잠금 파일(`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`), 생성된 파일, 대용량 데이터·로그, 이미지·바이너리.

## 3. 명령 출력을 줄인다
- 설치·빌드는 조용한 옵션(`-s`, `--silent`, `-q`)으로. 실패했을 때만 로그를 본다.
- 테스트는 바꾼 부분만: `npm test -- <경로>`, `pytest <파일> -q`, `vitest run <경로> --reporter=dot`.
- 타입 검사·린트는 해당 패키지/파일만.
- 긴 로그는 통째로 보지 않는다: `tail -n 50`, `grep -n "Error"`로 필요한 줄만.
- `git diff`는 `--stat`으로 먼저 보고, 필요한 파일만 자세히.

## 4. 답변을 줄인다
- 답변은 "바꾼 파일과 이유"만. 코드 전체를 다시 출력하지 않는다.
- 수정은 바뀌는 부분만 고친다(파일 전체 다시 쓰기 금지).
- 확인 질문은 정말 막혔을 때만. 정할 수 있는 건 안전한 기본값으로 정하고 한 줄로 알린다.
- 사과, 반복 요약, "이제 ~하겠습니다" 같은 예고 문장을 쓰지 않는다.

## 5. 헛도는 것을 막는다
- 같은 오류로 3번 실패하면 멈추고 보고한다(같은 수정 반복 금지).
- 큰 변경은 계획을 먼저 보여주고 승인받는다 — 잘못 간 방향을 통째로 다시 하는 게 가장 비싸다.
- 요청 밖 리팩터링, 요청하지 않은 기능 추가를 하지 않는다.

## 6. 세션을 관리한다
- 주제가 바뀌면 새 세션으로 시작한다. 긴 대화는 매 요청마다 앞 내용을 다시 읽는다.
- 끊기 전에 `docs/progress.md`에 3줄 기록 → 새 세션은 그것만 읽고 시작.
- 대화 압축 기능(예: Claude Code의 `/compact`)은 큰 작업 단위가 끝났을 때 쓴다.

## 7. 일을 나눠 맡긴다
- 넓은 탐색(여러 폴더를 훑어야 하는 조사)은 하위 에이전트에게 맡기고 **결론만** 받는다. 파일 내용이 내 대화에 쌓이지 않는다.
- 단, 파일 몇 개만 보면 되는 일은 직접 한다. 하위 에이전트는 시작할 때마다 비용이 든다.
- 단순 작업(이름 바꾸기, 포맷 맞추기)은 가볍고 싼 모델로, 설계·디버깅은 강한 모델로.

## 8. 캐시를 살린다
- 지침 파일·기준 문서는 자주 바꾸지 않는다. 앞부분이 같으면 캐시가 재사용돼 비용이 준다.
- 매번 바뀌는 내용(날짜, 진행 상황)은 지침 파일이 아니라 `docs/progress.md`에 둔다.

---

## 지침 파일에 넣을 줄 (복사용)

```markdown
## 토큰 절약
- 탐색은 grep/glob으로 범위를 좁혀서. 레포 전체 훑기 금지
- 읽지 말 것: node_modules, dist, build, coverage, 잠금 파일, 생성된 파일, 로그
- 큰 파일은 필요한 범위만. 방금 수정한 파일은 다시 읽지 말 것
- 테스트는 관련 파일만: <파일 하나 테스트 명령>
- 설치·빌드는 조용한 옵션으로. 실패 시에만 로그 확인. 긴 로그는 tail/grep으로
- 응답은 짧게: 바꾼 파일과 이유만. 코드 전체를 다시 출력하지 말 것
- 같은 오류 3번 실패하면 멈추고 보고
- 큰 변경(파일 5개 이상, 구조 변경)은 계획 먼저, 승인 후 진행
- 작업 끝나면 docs/progress.md에 3줄 이내 기록(한 일, 남은 일, 결정 사항)
```
