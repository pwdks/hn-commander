# 하네스 엔지니어링 (CLI 환경)

## 1. 한 줄 정의
모델은 그대로 두고, 모델이 일하는 **환경(지침·도구·권한·검증·기록)** 을 설계해서 결과를 좋게 만드는 일.
CLI 환경에서는 그 환경의 대부분이 **프로젝트 안의 `.md` 파일과 설정 파일**이다.

## 2. 하네스의 5요소와 CLI에서의 모양

| 요소 | 무엇을 정하나 | CLI에서 담는 곳 |
|---|---|---|
| 지침 | 규칙, 금지 사항, 작업 방식 | `CLAUDE.md` / `AGENTS.md` (세션마다 자동으로 읽힘) |
| 컨텍스트 | 무엇을 언제 읽게 할지 | `docs/` 아래 문서 + 지침 파일의 "문서 안내" 목록 |
| 도구·권한 | 무엇을 읽고 고치고 실행해도 되는지 | 각 CLI의 설정 파일(허용/금지 명령, 샌드박스 모드) |
| 검증 | 일이 끝났는지 누가 판단하나 | 테스트·빌드·린트 명령 (지침에 정확한 명령을 적음) |
| 기록·상태 | 세션이 끊겨도 이어갈 수 있게 | `docs/progress.md`, `docs/decisions.md` |

> 참고: Claude Code는 `CLAUDE.md`, Codex CLI 등 여러 도구는 `AGENTS.md`를 읽는다. 둘 다 쓰려면 한쪽에 내용을 두고 다른 쪽은 "AGENTS.md를 따를 것" 한 줄만 둔다.

## 3. 원칙

### 3.1 지침 파일은 짧게, 나머지는 안내만
- 지침 파일은 **매 요청마다 통째로 읽힌다.** 길수록 매번 토큰이 든다.
- 지침 파일에는 절대 규칙, 명령어, 문서 안내만 둔다. 상세 설명은 `docs/`로 빼고 "언제 무엇을 읽을지"만 적는다.
- 목표 분량: 지침 파일 100줄 이하.

### 3.2 규칙은 확인할 수 있게 쓴다
- 나쁜 예: "코드를 깔끔하게 작성할 것"
- 좋은 예: "함수는 50줄 이하. 새 의존성 추가 전에 물어볼 것. 커밋 전에 `npm test` 통과."
- 모델이 "지켰는지" 스스로 판단할 수 있는 문장만 쓴다.

### 3.3 판단은 기계에게
- "테스트가 통과했다"는 모델의 말이 아니라 **명령 실행 결과**로 확인한다.
- 지침에 검증 명령을 정확히 적는다: 전체 테스트, 파일 하나 테스트, 타입 검사, 린트.
- 모델에게 "실행하지 않은 결과를 지어내지 말 것, 못 돌렸으면 '확인 못 함'이라고 적을 것"을 규칙으로 둔다.

### 3.4 권한은 역할에 맞게 좁게
| 권한 단계 | 할 수 있는 것 | 맡길 역할 |
|---|---|---|
| 읽기 전용 | 파일 읽기, 검색 | 지휘, 설계, 검토 |
| 수정 | 파일 수정 | 구현, 테스트, 문서 |
| 수정+실행 | 파일 수정, 명령 실행 | 디버깅, 통합, 최적화 |

- 되돌리기 어려운 일(삭제, 강제 푸시, 배포, 외부로 보내기)은 지침에 "먼저 물어볼 것"으로 적고, CLI 설정에서도 금지/확인 대상으로 둔다.
- 비밀 파일(`.env`, 키, 인증 파일)은 읽기 금지로 적는다.

### 3.5 큰 일은 계획 → 승인 → 실행
- 파일 5개 이상 또는 구조 변경이면 먼저 계획(바꿀 파일, 방법, 위험)을 보여주고 승인 후 진행.
- 계획은 `roles/01-architect.md` 형식(요점 3~7개)을 쓴다.

### 3.6 세션은 끊겨도 된다 — 기록이 이어준다
- 세션 시작: `docs/progress.md`부터 읽는다.
- 작업 끝: 3줄 이내로 기록(한 일 / 남은 일 / 결정 사항).
- 기존 방침과 다르게 정한 것은 `docs/decisions.md`에 한 줄 표로 남긴다.
- 대화가 길어지면 새 세션으로 시작해도 기록만 읽으면 이어갈 수 있어야 한다.

### 3.7 실수는 하네스로 고친다
모델이 같은 실수를 두 번 하면, 대화로 타이르지 말고 **지침 파일에 한 줄을 추가**한다.
- 예: 잘못된 폴더에 파일을 만듦 → "새 파일은 `src/` 아래에만 만든다"
- 예: 테스트를 안 돌림 → "작업 끝나기 전에 `npm test -- <바꾼 파일>` 실행"
- 한 달에 한 번 지침 파일을 다시 읽고, 안 쓰는 규칙은 지운다(짧게 유지).

## 4. 작업 흐름 (기본 루프)

```
요청 → (큰 일이면) 설계 요점 → 승인 → 구현 → 검증 명령 실행
     → 실패하면 디버깅(최대 2~3회) → 검토 → 기록
```

- **반복 한도**를 정한다: 같은 오류로 3번 실패하면 멈추고 원인·시도·가설을 보고.
- **멈출 조건**을 정한다: 요청 밖 범위를 건드려야 하면 멈추고 묻는다.

## 5. 여러 역할로 나눌 때 (멀티 에이전트)
- 지휘 역할이 요청을 작업으로 나누고(`roles/00-orchestrator.md`), 각 작업은 하나의 역할이 맡는다.
- 각 작업에는 **목표, 완료 조건, 역할 지침, 앞선 작업 결과 요약**만 넘긴다. 전체 대화를 넘기지 않는다.
- 파일을 고치는 작업은 한 번에 하나씩. 읽기만 하는 작업은 동시에 돌려도 된다.
- 하위 작업이 다시 다른 에이전트에게 넘기지 않게 한다(재위임 금지).
- 마지막에 통합 역할이 작업 사이의 어긋남을 맞추고, 검토 역할이 다시 본다.

### 역할 지침을 CLI에 연결하는 방법
- **가장 단순**: 요청 앞에 "`docs/roles/04-reviewer.md`를 따라 검토해줘"라고 적는다.
- **지침 파일에 안내**: `CLAUDE.md`/`AGENTS.md`에 "검토 요청이면 `docs/roles/04-reviewer.md`를 따를 것".
- **Claude Code 서브에이전트**: 역할 파일을 `.claude/agents/<이름>.md`로 복사하면 하위 에이전트로 쓸 수 있다. 맨 위 머리말(`name`, `description`)은 그대로 두면 된다. 읽기 전용 역할은 `tools: Read, Grep, Glob` 줄을 추가해 권한을 좁힌다.
- **반복 명령**: 자주 쓰는 요청은 Claude Code의 `.claude/commands/<이름>.md`(슬래시 명령)로 만든다.

## 6. 점검표 — 하네스가 갖춰졌나
- [ ] 지침 파일이 100줄 이하이고, 절대 규칙·명령어·문서 안내가 있다
- [ ] 테스트·빌드·린트 명령이 정확히 적혀 있다 (파일 하나만 돌리는 방법 포함)
- [ ] 읽지 말아야 할 폴더/파일이 적혀 있다
- [ ] 되돌리기 어려운 일은 "먼저 물어볼 것"으로 적혀 있다
- [ ] `docs/progress.md`, `docs/decisions.md`가 있고 기록 규칙이 있다
- [ ] 반복 한도와 멈출 조건이 있다
- [ ] 역할 지침이 필요한 만큼 `docs/roles/`에 있다
- [ ] 같은 실수가 두 번 나오면 지침에 한 줄 추가하는 습관이 있다
